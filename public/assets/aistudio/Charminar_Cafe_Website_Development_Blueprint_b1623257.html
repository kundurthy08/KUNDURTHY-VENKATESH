This document is the working specification to give an IDE-based development workflow or an AI coding assistant. It defines the product, the expected customer and staff flows, the suggested system design, the staged build plan and the release checks. It is deliberately written so that the project can start with a polished public website and expand into operational software without rebuilding the foundation.

Important project assumption: Charminar Café is treated as a Hyderabad-inspired Indian café brand. The actual café photographs, final menu, prices, address, operating hours, logo, payment provider, delivery coverage and policies must be supplied and approved by the owner. Do not invent these details or publish sample data as real business information.

01. Product vision

Product name: Charminar Café Digital Experience.

Positioning: A warm, contemporary Indian café identity with visual references to Hyderabad's heritage — arches, jaali patterns, brass details, deep green, terracotta, cream and antique gold. The brand must feel authentic and welcoming, not like a monument-themed tourist template.

Core promise: The website should communicate the atmosphere of the physical café while making it easy to explore the menu, place an order, reserve a table and connect with the business.

Brand experience

Immersive 3D entry, elegant transitions, food photography, responsive storytelling and consistent physical-to-digital aesthetics.

Business utility

Accurate menu, order and reservation workflows, staff operations, reporting and controlled content updates.

Performance

Fast 2D fallback, compressed 3D assets, lazy loading and a usable experience on mid-range mobile devices.

Maintainability

Reusable components, documented business rules, role-based access and clear separation between UI and data.

03. Main user journeys and system flows

A. Browse the café

Open website→3D hero / 2D fallback→Explore story & menu→Location / contact / CTA

The 3D scene is an enhancement, not a gate. Navigation, menu and contact actions must remain accessible if WebGL is unavailable, the device prefers reduced motion, or the 3D file fails to load.

B. Online order

Choose items→Customise→Cart validation→Pickup / delivery→Payment→Confirmed order
  1. Load current menu and availability from the server.
  2. Customer selects items, quantities and permitted modifiers.
  3. Server revalidates product status, price, quantity, tax and any minimum order rules. Never trust client-side totals.
  4. Customer selects pickup or an enabled delivery method and supplies only the required contact details.
  5. Server creates a pending order and payment attempt where online payment is enabled.
  6. Payment is marked successful only after a verified server-side gateway confirmation/webhook. Never rely only on the browser redirect.
  7. Confirmed order appears in the staff order queue and customer receives a confirmation through enabled channels.
  8. Staff updates preparation and fulfilment status. Customer sees the latest status where tracking is enabled.

Suggested order states: Draft → Pending Payment → Placed → Accepted → Preparing → Ready → Completed. Additional terminal states: Payment Failed, Cancelled, Refunded. Configure the exact transitions with the café owner. Record who changed each status and when.

C. Table reservation

Select date & time→Party size→Check capacity→Submit request→Confirm / decline

Prevent overlapping bookings using server-side capacity checks and a database transaction or equivalent concurrency-safe reservation mechanism. Define slot duration, grace period, opening hours, blackout dates, maximum party size, cancellation rules and whether staff approval is required. Do not show a slot as available based only on stale browser data.

D. Staff order handling

New order alert→Accept / reject→Prepare→Ready→Hand over / complete

Provide clear status filters, order timestamps, item modifiers, customer instructions and an exception path for unavailable items. Cancellation, refund and price changes require authorised roles and an audit record.

04. Suggested technical architecture

Use a modular full-stack architecture. Keep the first release straightforward; do not introduce microservices unless real scale or integration requirements justify them.

Frontend

Next.js with React and TypeScript. Responsive pages, reusable UI, accessible navigation and server-rendered SEO content.

3D layer

Three.js with React Three Fiber, Drei helpers where useful, Blender for asset preparation, GLB/glTF delivery.

Backend

Next.js server routes/server actions or a separately hosted Node API. Validate every write on the server.

Database & auth

PostgreSQL (managed provider such as Supabase is an option), secure authentication and role-based access.

Media

Object storage or an image CDN for optimised photographs, 3D files and textures. Keep source assets separately backed up.

Hosting

Frontend hosting such as Vercel or equivalent; managed database/storage; custom domain with HTTPS.

3D integration workflow

  1. List every downloaded file with filename, extension, size, source URL/vendor and licence terms.
  2. Preview each model in Blender or a glTF viewer. Check missing textures, material errors, scale, pivot/origin and animation clips.
  3. Choose the assets that support the brand story. Avoid placing every model on the homepage.
  4. Optimise in Blender or an appropriate glTF pipeline: remove hidden geometry, reduce unnecessary polygons, resize textures, reuse materials and compress geometry/textures where compatible.
  5. Export as GLB for convenient web delivery. Keep editable source files and original downloads outside the production public folder.
  6. Load the hero scene dynamically. Show a branded poster or lightweight 2D hero while the scene loads.
  7. Use progressive enhancement: desktop may receive the richer scene; mobile receives a lighter scene or static visual based on device capability and performance.
  8. Test keyboard access, reduced-motion preference, touch controls, low-memory devices and WebGL failure.
Asset rights: Verify that each downloaded model, texture, font and sound permits commercial website use and modification. Keep proof of licence. Attribution requirements must be followed.

Performance rules for 3D

  • Set a measurable initial 3D payload budget with the developer; target a small first-load scene and load secondary models only when needed.
  • Use lazy loading, Draco/Meshopt geometry compression and KTX2/Basis texture compression when the toolchain supports them.
  • Limit real-time lights, shadows, transparent materials, post-processing and draw calls.
  • Pause or reduce rendering when the scene is off-screen or the tab is hidden.
  • Respect prefers-reduced-motion and provide a visible “Skip animation” or equivalent accessible route.
  • Do not make the menu, cart or navigation depend on the 3D canvas.

Experience rules

  • Design mobile-first; primary actions must be reachable without exploring the 3D scene.
  • Use consistent header, footer, buttons, cards, typography, spacing and focus states.

07. Business logic specification

Menu and pricing

  • Each menu item has name, description, category, base price, image, active/inactive state, availability schedule, tax classification, dietary labels and optional allergen information.
  • Modifiers/add-ons have their own price and allowed selection rules (required/optional, min/max selections).
  • Server calculates line totals, discounts, taxes, fees and final total from current database values.
  • When an item becomes unavailable, block new orders for it and show a clear message; never silently substitute another item.
  • Keep a price snapshot on each order so historical receipts do not change when menu prices are updated.

Cart and checkout

  • Validate item availability and modifier selections again at checkout.
  • Define pickup/delivery availability, service hours, minimum order, delivery zones/fees and estimated preparation time with the owner.
  • Use an idempotency key for order creation/payment initiation to avoid duplicate orders on repeated clicks or network retries.
  • Store payment provider reference and status. Do not store card numbers, CVV or sensitive payment credentials.
  • Support payment failure, retry, cancellation and refund paths according to provider capability and café policy.

Reservations

  • Define table capacity or booking-slot capacity, service hours, booking duration, buffer time, lead time and blackout periods.
  • Use atomic server-side checks to prevent two users booking the same capacity.
  • Define pending, confirmed, declined, cancelled, completed and no-show states as required.
  • Send confirmations only after the reservation reaches the configured confirmed state.

Reporting definitions

Define metrics before building charts. Clearly label order date versus payment date and gross versus net figures. Reports must reconcile to the underlying orders and payment records.

Data and money handling

  • Use integer minor units (for example paise) or a suitable fixed-precision decimal for money; never use floating-point arithmetic for financial totals.
  • Store timestamps consistently in UTC and display them in the branch's configured local timezone.
  • Use database constraints and transactions for order creation, stock movements and reservation capacity.
  • Define retention, deletion and export policies for customer data with the owner and applicable law.

09. Phase-wise development roadmap

Recommended sequence: agree scope, build a dependable foundation, then add operational features. The estimates below are indicative for one small experienced team and will change with asset quality, integrations and owner feedback.

Phase 0 — Discovery & requirement sign-off2–4 working days
Work: owner interview, business model, branch count, menu collection, customer/staff journeys, order and reservation rules, payment/POS decisions, content and asset rights review.
Deliverables: signed scope, page map, workflow diagrams, requirements register, content checklist, risks and acceptance criteria.
Exit gate: owner approves scope, real business details and release-one features.
Phase 1 — Brand, UX and 3D asset audit3–6 working days
Work: visual direction, design tokens, responsive wireframes, page prototypes, 3D asset inventory, model tests and performance budget.
Deliverables: approved UI design, component reference, asset register, optimised hero-scene proof of concept and mobile fallback.
Exit gate: owner approves the design and the chosen 3D assets render reliably on target devices.
Phase 2 — Project foundation & public website5–8 working days
Work: repository, environments, CI checks, shared layout, homepage, story, menu display, contact/location, SEO basics and content structure.
Deliverables: responsive staging website with placeholder content clearly marked until approved content is received.
Exit gate: all public pages work on mobile and desktop; no critical accessibility or navigation defects.
Phase 3 — 3D experience integration4–8 working days
Work: Blender optimisation, GLB loading, scene lighting, camera path, scroll interaction, fallback poster, reduced-motion behaviour, loading and error states.
Deliverables: integrated hero experience and documented asset pipeline.
Exit gate: 3D experience meets agreed performance budget and never blocks core navigation.
Phase 4 — Backend, database & admin6–10 working days
Work: database migrations, authentication, roles, menu CRUD, content/offer management, admin dashboard and audit logging.
Deliverables: protected admin portal and tested data services.
Exit gate: unauthorised users cannot access protected functions; menu changes appear correctly on the public site.
Phase 5 — Orders, payments & reservations8–15 working days
Work: cart, checkout, pricing validation, order state machine, payment sandbox/webhooks, reservation capacity logic and notifications.
Deliverables: end-to-end ordering/reservation flows in staging.
Exit gate: successful, failed, duplicate and interrupted payment scenarios are handled; capacity conflicts are prevented. POS/delivery integrations are separate scope items.
Phase 6 — Reporting, content and operational readiness3–6 working days
Work: dashboard definitions, report reconciliation, real menu/content entry, policy pages, staff training and support procedures.
Deliverables: owner-approved content, tested reports, staff guide and launch checklist.
Exit gate: owner signs off menu, prices, taxes, policies, notifications and operational workflows.
Phase 7 — UAT, production launch & stabilisation4–7 working days plus monitoring
Work: user acceptance testing, security review, backups, domain/DNS, HTTPS, production secrets, smoke tests and monitored rollout.
Deliverables: production website, deployment notes, rollback plan and handover pack.
Exit gate: all launch-blocking tests pass and owner approves go-live.

Planning note: The phases can overlap modestly after design sign-off. Do not compress payment, security, data backup or UAT work just to meet a launch date.

Test layers

LayerWhat to verify

End-to-end testsBrowse menu → add to cart → checkout → payment result → staff fulfilment; reservation request → staff decision.

Performance testsCore Web Vitals, image payload, 3D load time, memory use and slow-network behaviour.

Accessibility testsKeyboard use, focus visibility, semantic headings, contrast, labels, screen-reader basics and reduced motion.

Minimum test scenarios

  • Menu loads correctly when the 3D scene is disabled or fails.
  • Unavailable products cannot be ordered.
  • Changing a displayed price in the browser cannot change the server-calculated order total.
  • Repeated checkout clicks do not create duplicate orders or charges.
  • Payment success is recognised only after verified provider confirmation.
  • Payment failure, cancellation, delayed webhook and refund cases are handled.
  • Two customers attempting the final reservation capacity cannot both be confirmed.
  • Staff roles cannot access owner-only settings.
  • Admin changes are reflected on the public website within the agreed refresh/cache interval.
  • Mobile menu, cart and forms work with touch and keyboard.
  • 3D assets load on supported devices and a usable fallback appears elsewhere.
  • Backup restoration is tested, not merely assumed.

Suggested release targets

  • No open critical or high-severity defects at launch.
  • All critical customer journeys pass on supported browsers and target mobile devices.
  • Agree a mobile performance budget; measure with Lighthouse and real-device testing rather than relying on a single score.
  • All menu, tax, pricing, payment and reservation rules signed off by the owner.

11. Security, privacy and compliance

  • Enforce server-side authorisation on every admin API and mutation. Hiding a button is not access control.
  • Use a trusted authentication provider or secure, maintained session implementation. Require strong owner/admin credentials and MFA where available.
  • Keep secrets in environment variables or a secrets manager; never commit production keys to Git or expose them in frontend bundles.
  • Validate and sanitise user input. Apply rate limits and bot protection to public forms, login, checkout and reservation endpoints.
  • Verify payment webhook signatures and make webhook processing idempotent.
  • Use HTTPS, secure cookies, appropriate security headers, dependency scanning and least-privilege database credentials.
  • Collect only necessary customer data. Publish clear privacy and cookie notices as applicable; define retention and deletion procedures.
  • Do not store card data or authentication secrets belonging to payment providers.
  • Back up the database automatically and test a restore before launch. Restrict access to backups.
  • Confirm applicable Indian tax, consumer, privacy and payment requirements with the café's accountant/provider or qualified adviser. The development team should not invent tax rates or legal wording.

Deployment sequence

  1. Create Git repository and protect the main branch.
  2. Set up local, staging and production environment variables separately.
  3. Configure managed PostgreSQL, storage buckets, auth redirect URLs and database backups.
  4. Connect the repository to the hosting provider and enable build/deployment checks.
  5. Run lint, type-check, unit and integration tests on every pull request.
  6. Deploy to staging; run end-to-end, visual, performance and owner acceptance tests.
  7. Apply reviewed database migrations using a controlled deployment step.
  8. Configure custom domain DNS and HTTPS. Verify redirects and canonical URL.
  9. Configure production payment credentials and webhook endpoint only after provider approval and a successful sandbox test.
  10. Publish approved content, run production smoke tests and monitor logs, errors and payment/order events.
  11. Keep the previous stable deployment available for rollback. Document how to revert application code and safely handle database migrations.

Monitoring after launch

  • Track application errors, API failures, database health and 3D asset loading failures.
  • Alert the owner/maintainer about failed payment webhooks and orders stuck in unexpected states.
  • Review backups, uptime, dependency/security updates and storage usage on a defined schedule.
  • Keep an incident contact, escalation procedure and rollback instructions.
